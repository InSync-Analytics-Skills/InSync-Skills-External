# What the scripts enforce

Read this when the user asks why the sheet shows (or leaves out) something, or before changing a
script. On a normal run you do not need it: `prepare_revisions.py` and `build_revision_xlsx.py`
apply every rule below by themselves, and `sanity_check.py` checks the result. Never override
one of these rules by hand or re-create the logic in the conversation.

## The evidence table (left half of the sheet)

⛔ **The evidence layer is LOCKED.** The evidence table is settled — do not add revision scores, breadth/velocity readouts, gauges or dashboards to them, and do not restructure them. All future work happens on the right-hand panel.

1. **Revision Summary** — one sheet, two halves.
   - **Left, the evidence table — TWO period blocks**: `NEXT QUARTER - {q}` then `FY{fy1}`, each with `Pre-Print | [T+10] | [T+40] | Current | Δ$ since print | %Δ since print | YoY % | Seq % | Low | High | Broker cnt` (the annual block has no Seq column; its YoY compares the FY1 estimate to the last reported fiscal year). Both blocks use the SAME since-print anchors, so the annual shows how much of the quarterly revision the Street has carried through to the full year. Anchors are STRICTLY earnings-anchored and chronological: Pre-Print always shows; **T+10 and T+40 become eligible ONLY when that many days have actually elapsed since the print** (fresh print → just Pre-Print → Current; after day 40 → all four eligible). NO calendar anchors — never a −30D-style column, which can put a pre-print date to the right of a post-print one. The Δ pair always compares Current to Pre-Print (the full post-print revision), and every intelligence signal uses the same since-print basis. Section order FIXED: **Income Statement → Segment Revenue → Key Metrics (KPIs) → Balance Sheet → Cash Flow** (no Basic EPS/Basic Shares — diluted only; no duplicate FCF variants). Balance-sheet rows are displayed but carry a low materiality weight (0.35) and their own layer, so cash and debt swings never crowd the P&L out of the headline movers.
   - ⛔ **ANCHOR ELIGIBILITY IS CALENDAR-GATED; ANCHOR VISIBILITY IS INFORMATION-GATED.** An eligible T+10 or T+40 column renders only when it carries a consensus snapshot DISTINCT from its neighbours, tested ROW BY ROW, never on header dates: the column stays if any displayed row has a value there that differs from its value at the previous kept anchor and from its Current value; if every row equals Current the column collapses into Current, if every row equals Pre-Print (no broker refresh inside the window) it collapses into Pre-Print. Pre-Print and Current are mandatory. The test runs PER BLOCK (quarter and annual independently, because brokers refresh the year on different days from the quarter) and the sheet lays out the UNION: in a block where the column would duplicate its neighbour the cells are left EMPTY and that block's date-row cell reads `Same as Current` / `Same as Pre-Print`. Never two columns of identical numbers. The prepare script writes `contract.anchorView` (per block: `distinct`, `sameAs`); the builder only reads it. When the T+10 vintage equals the Current vintage the sheet renders Pre-Print | Current, and the hold is stated in the Revision path line, not in a duplicate column.
   - ⛔ **The date row carries consensus VINTAGES, never calendar cuts.** Each column's date is the LATEST update that column contains in that block (the pre-print vintage under Pre-Print, the last update on or before day 10 under T+10, the latest update under Current) — "consensus as of 09/22" is the safe statement when three rows were refreshed on 09/22 and the rest on 09/19, and the row can never read out of order (e.g. 09/05 → 09/19, not 09/09 → 09/20 → 09/19). The cut dates stay in `contract.cuts` for audit; per-row vintages stay on every item (`preD / t10D / t40D / curD`). The panel's status band states the same vintage (`consensus as of 19 Sep 2026`) beside the masthead's `Prepared` run date: the run date says when the analysis was done, the vintage says what consensus it holds, and the gap between them is itself information — never stamp the run date on the Current column.
   - ⛔ **Stale is not flat.** A row whose latest snapshot predates the print was never refreshed after it: its Δ cells print `–` (unknown, not zero), its Current value is muted, and it is excluded from breadth, the curated lists and the evidence read (`per.q.stale`). When at least a third of the rows are stale the band says so. When NO row carries a post-print snapshot the band states `No consensus update has been published since the print (last vintage …)`, every Δ prints `–`, no revision path is classified and the computed panel fallbacks stand down (`intel.dataState.key = no-post-print-update`); a measured ZERO is treated the same way on the panel — when rows were refreshed but no eligible line moved (breadth 0 up / 0 down) the `Result:` fallback says the consensus is unchanged and the computed fallbacks stand down, and anywhere on the panel a move that rounds to `0.0%` prints unsigned and a `$0m` contributor is not printed (the zero-Δ rule, panel side); when no row has a pre-print vintage inside the lookback the band says the since-print revision cannot be measured (`no-pre-print-anchor`). In the FRESH phase, when the refreshed broker count on the headline line is below half the pre-print count, the band states `Current consensus carries 4 of 18 pre-print brokers` — the one place a coverage statistic belongs in the table area, because the %Δ is then partly a change of sample (`intel.coverage`, from the pre-print count stored on every row as `preCnt`).
   - ⛔ **Visible is not the same as revisable.** Every selected row stays VISIBLE whatever its coverage (a one-broker RPO level is still information), but a row feeds a revision CONCLUSION — breadth, the curated Upgrades/Downgrades, the operating-evidence read, segment attribution, the revision path, the cross-horizon divergence — only when it has a pre-print value to revise from, was refreshed after the print and carries at least 3 brokers (`ELIG` in the prepare script, `intel.breadth.lowCoverage` counts the rest). A `Current X` / `Non-Current X` KPI whose consensus exceeds its parent `X` fails the Current + Non-Current = Total identity and cannot be reconciled: that row leaves the visible table and is kept with its values and the reason in `contract.excluded` (e.g. Current Bookings at $100bn against Bookings at $40bn on one broker). A Δ whose DISPLAYED value rounds to zero (1dp for money and shares, 2dp per share, whole bps for % rows) prints `–` with no arrow and no colour, so a −$0.0001 EPS move never shows as `0.00 ▼`. The `%Δ since print` column shows one decimal (`4.3% ▲`), and a %Δ that rounds to `0.0%` is a `–` as well, even when Δ$ is not.
   - ⛔ **KPIs are ordered by PARENT-CHILD FAMILY, families ranked by broker depth — never by code number.** KPIs publish as families (Total / Current / Non-Current / Change in / Net Adds / Average / derived ratios), and components that SUM to a parent sit directly under it: `Total RPO → Current RPO → Non Current RPO → Change in RPO`, `Total Billings → Current Billings`, `Total Bookings → Current Bookings → Book to Bill` (a derived ratio joins its numerator's family; a qualified label like "Customers with TTM Product Revenue > $1M" is a child of `Customers`). Families sort by their deepest broker count so the best-covered family leads the block; within a family the order is parent → Current → Non-Current → derived → ratio → qualified children. Enforced by `kpiOrder()` in the prepare script — do not hand-reorder.
   - ⛔ **Balance Sheet is FIVE rows, decided by broker depth — never the whole balance sheet.** The BS is context, not the argument: headline cash, Total Assets, Total Liabilities, Total Debt, Net Debt. Two selection rules, both enforced by the prepare script and disclosed in `contract.json` (`flowNotes`, never printed): **(a) Cash** — the feed publishes up to three overlapping cash lines (incl. securities / cash only / securities only); keep the deepest-covered one, tie to the inclusive headline. **(b) Debt basis** — Total Debt and Net Debt each exist Ex-Operating-Lease and Incl-Operating-Lease; pick ONE basis for BOTH rows from combined broker depth, a tie going to Incl-lease. Never mix bases: an Ex-lease Total Debt above an Incl-lease Net Debt is the same defect as a Non-GAAP PBT above a GAAP tax line.

## Panel mechanics the builder owns

   - **NO methodology/provenance footer on EITHER sheet.** The basis choices (flow, debt basis, cash-line, source), the history-matrix legend (forward-filling, Δ definition, colour key) and the prepared/print dates in footer form all stay in `contract.json` for audit and never print — the reader does not need the machinery, and the masthead already carries the dates. ⛔ **Nothing prints under the summary table either**: unit cautions, the segment-coverage disclosure and family-identity exclusions live in `contract.scaleNotes` / `contract.excluded` and in the build log, and the run summary in chat relays them. There is no panel disclosure footer: the panel explains itself or it is wrong.

   - ⛔ **Panel prose is pre-wrapped by the builder to ONE VISUAL LINE PER ROW, at the table's own row height.** Never put a long sentence in one merged cell and call `setHt` to grow the row: the row is SHARED with the evidence table on the left, so tall panel text stretches the table and wrecks its formatting. `wrapLines()` + `pLine()` keep every row at normal height, so the two halves stay independent — no stretching on the left, no clipping on the right.

   - **Revision PATH, not just magnitude.** `intel.revisionPath` classifies *when* the move landed across the anchors — Reset & Hold / Reset & Build / Spike & Fade / Dip & Recover / Late Revision / Unsettled. Two identical +5% revisions mean opposite things: a front-loaded reset means consensus repriced on the release and has not moved since; a still-building one means estimates are still rising. One line, core metrics only — and the path describes the CORE earnings revision: an `Exception.` line (`Exception. On EBITDA, estimates have continued to rise since the print.`) prints only when the divergent series is Revenue, EPS or EBITDA; a secondary metric (FCF, working capital, a segment) still moving after the print is not an exception worth a line.

2. ⛔ **There is NO second sheet.** The snapshot-by-snapshot history matrix is still computed by the prepare script (into `contract.history`, built LAST, after the one-flow policy and row trimming) because the anchors, revision-path classification and the whole intelligence layer are sliced from it — but it renders NOWHERE. Do not re-add a Revision History tab to the builder; anyone needing the raw matrix reads `contract.json`.

## Income-statement policy

**Interest block — the net line makes its components redundant.** `Interest Expense` (`IS_P_141/142`) and `Interest Income` (`IS_P_157/158`) are shown ONLY when no net interest line survives the flow policy, and the narrower `Net Interest Income/Expenses` (`IS_P_1003/1004`) is likewise suppressed whenever the broad `Net Interest & Other Income/Expenses` (`IS_P_115/116`) survives — two net lines state the same fact twice. Where a net line exists, the components restate it and add sub-$100m rows to a multi-billion-dollar statement; the suppression is disclosed in `flowNotes` (audit only).

**Flow policy — ONE flow for the whole Income Statement (uniform across every sub-industry, enforced by the prepare script):** the statement NEVER mixes flows — a Non-GAAP PBT above a GAAP tax line is a broken P&L. The prepare script decides ONCE per company: the **Non-GAAP flow leads when the adjusted chain is broadly covered** (median adjusted/GAAP broker-count ratio across all paired lines ≥ 75%), **otherwise the whole statement is GAAP** (the common case when adjusted COGS/Opex/Tax carry only 10–15 brokers against 40 GAAP). Every line then follows that one flow, so the statement ties top to bottom. The MAIN ITEMS — **EBITDA, EBIT, NET INCOME, EPS** — additionally show the other flow as a muted, indented twin when both flavours exist; the same both-flows treatment applies to industry-specific GAAP/non-GAAP pairs (e.g. banking or REIT lines) that reach the sheet through the KPI/segment universe. A line whose on-flow flavour is not published takes the other flavour unmarked (the sheet carries no legend since footnotes left it; the slots so filled are listed in `contract.flowNotes`). ⛔ **Every GAAP/adjusted pair must be REGISTERED in the `PAIRS` list, including `IS_P_115`/`IS_P_116` (Net Interest & Other Income/Expenses), `IS_P_1003`/`IS_P_1004` (Net Interest Income/Expenses) and the interest components `IS_P_141`/`IS_P_142` and `IS_P_157`/`IS_P_158`.** An unregistered twin is not recognised as a twin: it escapes the flow policy, shows as a second independent row beside its own sibling, and its broker counts are excluded from the flow decision. When adding a line item to the statement, check whether it has an adjusted flavour and register the pair. Two adjusted variants of one line → the deeper broker coverage wins. The chosen flow and the full broker-count evidence stay in `contract.json` for audit — they do NOT print on the sheet.

## Segment roll-up (the full rule)

**First: the split that is exact in reported history.** When `raw/` holds at least 4 of the last 8 reported quarters of segment actuals (SKILL Step 4b), the prepare script looks for sets of segment rows that add up to Total Revenue within 0.1% in EVERY quarter where all members report, and within 2% on consensus. A company's reported split is exact quarter after quarter; a parent kept beside its own sub-rows, or rows that happen to sum near the total, is not (a reported split typically ties at 0.00% in every quarter, while the consensus roll-up below can keep a segment beside its own sub-rows). Among exact sets: more material rows (>= 3% of revenue) win, then the smaller worst-quarter gap, then business before geography before mixed, then the deeper shallowest member, more primary-series rows, the smaller consensus gap and the shorter set. The sibling rule applies; restated quarters (`R-1Q25`) are preferred over the original figures. The choice is logged and recorded in `contract.flowNotes`. When no set is exact (too little history, an eliminations line the feed does not publish) or the search exceeds its budget, everything below runs exactly as before.

⛔ **Segment Revenue shows ONLY rows that ROLL UP to Total Revenue — or the honest business split when the feed cannot roll up.** The prepare script sum-checks candidate SD revenue rows against `IS_P_101` (2% tolerance, on the next-quarter consensus plus the reported and year-ago actuals). **A subset is judged on at least two of those periods whenever the target has two**: a row with no reported actual (a pre-launch pipeline bucket, a broker-only construct) cannot make a subset reconcile on the consensus period alone, so International + one product + two pipeline rows cannot pass by arithmetic coincidence; a segment the company reported at the print always qualifies. Before the roll-up it drops VALUE-DUPLICATES — one series published under two codes ("Total Services - Revenue" and "Services - Adjusted Revenue" carry identical values every period), which otherwise lets a subset reconcile by counting a segment twice; the primary series (`SD_P_*`), then the deeper broker count, is kept (logged) — and TOTAL DUPLICATES by value as well as by label: a candidate within 1% of the top line in every judgeable period ("Revenue by Segment") is the whole, not a part (logged). **A broad candidate pool is handled, never abandoned:** the exhaustive subset search runs on at most 16 rows per group, so a business or geography group above 16 keeps its primary-series rows first and then the deepest-covered rows (logged as "set aside"). **Sibling completeness:** rows that share a labelled family — the same head (`Wholesale - North America`, `Wholesale - Greater China`) or the same tail (`Product A - Systems`, `Product B - Systems`) — belong to one published split, so a reconciling subset takes the family whole or leaves it alone; without this a channel-plus-product-plus-region mixture can sum to the top line by arithmetic accident and out-rank the reported split. Among reconciling subsets, more MATERIAL members win, then the tighter error, then more primary-series members (the company's reported split), then the deeper shallowest member, then the shorter subset — never the longer one, so five one-broker sub-rows cannot stand in for a real segment. Precedence: a basis-homogeneous family that reconciles → a reconciling business subset → **the deepest NON-OVERLAPPING business split covering ≥90% of revenue** (every period sums to at most the total, so a parent and its own child can never both be kept; a subset of primary-series rows beats one that needs a secondary row; the subset whose shallowest member is deepest-covered beats a sub-segment a handful of brokers model) → a reconciling geography group → a reconciling mixed business + geography subset → the mixed coverage split → unfiltered business rows. Geography is recognised by the LTCODE (`Geo`) OR by a label made only of place words (`U.S.`, `International`, `Rest of Asia Pacific`, `EMEA & Latin America`); a label carrying a business word (`U.S. Pharmaceutical`, `International Markets`) stays a business row, so a company whose reported split is itself geographic still reconciles through the mixed fallbacks. The coverage fallback exists because a published split can lack a component (e.g. no Hardware line is published): without it the roll-up could fall through to thin 1-broker geography rows and lose the segment that carried the whole revision. When it fires, the disclosure `Segment Revenue rows cover 94.6% of Total Revenue; the remainder is a component the estimate feed does not publish` goes to `contract.scaleNotes` and the build log (nothing prints on the sheet); relay it in the run summary. Segment labels drop their metric suffix (" - Revenue", " - Adjusted Revenue", and a bare trailing "Revenue": `Oncology Revenue` → `Oncology`); a QUALIFIED metric tail becomes a parenthetical basis — `Wholesale - Core Brand Revenue` → `Wholesale (Core Brand)`, `Products - Enterprise Revenue` → `Products (Enterprise)` — and when the head is a generic word (`Geographic - Europe Revenue`) the qualifier alone is the label (general rule: the long vendor form would overflow the label column and the panel's shortener would print "Core Brand Revenue" as the segment); an adjusted basis shared by at least half the rows is hoisted once into the section title (`Segment Revenue (Adjusted)`). Total-duplicate rows like "Total Revenue by Geography" are always dropped. Still fetch ALL SD revenue codes — the filter needs the full group to judge the roll-up; relay the script's dropped-rows log in your summary if any were dropped.

## Materiality and selection

**Materiality is dollar-based, never %-based.** The prepare script converts every revision to dollars (per-share lines multiplied by share count), scales by revenue, floors out anything under 0.5% of revenue, weights by what the line says about earnings power, and keeps **one line per economic layer** (top / profit / cost / bottom / cash / segment ×2 / KPI). Capital-return and per-share-mechanical lines (DPS, dividends, buybacks, share counts) are barred from the headline unless fewer than three other lines qualify — a dividend repricing is capital allocation, not a change in the earnings outlook. Cost lines are judged on **margin**: COGS rising in line with revenue is neutral, not a downgrade. The suppressed count is engine bookkeeping and stays in `contract.json` (`intel.takeaways.suppressed`); it never prints.

**Drivers are selected by explanatory value, never by rank or by a fixed count.** Take contributors in size order until they account for 85% of the gross movement, cap at three per horizon, and always keep the largest offset — the largest move AGAINST the revision's direction, so a revenue cut lists its largest cuts first and keeps the segment that rose (e.g. Segment B −$900m first, Segment A +$200m as the offset) — a driver list without its offset misstates the revision. The remainder collapses into one `Other contributors:` line when collectively material and is dropped when it is not. One driver that explains the whole revision prints one line.

**Drivers follow the EARNINGS ENGINE, never the spreadsheet's structure.** `intel.engine` decomposes the pre-tax revision into signed dollar contributions from the P&L levers the sheet carries — revenue components, cost lines, provisions, and RATIO levers converted to dollars on the premium base (a loss-ratio cut of 90bp on $20bn of premium is +$180m of earnings, the largest lever on an auto insurer's sheet and invisible in any revenue stack). "What Drove the Revision" leads with that stack; the segment breakdown renders in full only when the dominant lever IS the top line, and collapses to one mix line otherwise. Aggregates are excluded, written premium is a leading indicator not an earnings input, and the loss-ratio family is deduped against its own components.

**Economic direction, not mathematical sign.** An inverted line whose raw direction reads contradictory is restated in its intuitive form: a tax-expense move prints as the ETR in bps (`▼ ETR +22bp`), a cost move as the margin it cost. The reader must never need to know a line is inverted to read the arrow.

**The curated lists carry independent findings that pass an INVESTMENT RELEVANCE filter, never echoes.** After materiality ranking, a line that is merely the accounting or cash-flow consequence of the primary operating revision (working-capital swings, deferred taxes, FX effects, share-count mechanics) cannot fill a curated slot — "Change in Working Capital +$37m" is a consequence, not a thesis-relevant revision (barred like capital return, admitted only when fewer than three thesis-relevant lines qualify). And when the operating-evidence contradiction lives in one KPI family, a materially weaker SIBLING from that family must not stand in a slot as the story's representative ("Current RPO −0.5%" for a family whose Change in RPO fell 15% misstates the story — the Variant owns the family; a sibling qualifies only at half the strongest contradicting move or more). Selection only: the locked parent/child ordering of the KPI table is untouched. The resolved revenue and EPS anchors are excluded (the Result line owns them), the whole bottom layer with them (net income restates EPS), a flat-rate tax move is excluded outright (tax dollars rising because profits rose is not a downgrade — with a real rate move, the ETR in bps is the finding), and an aggregate is dropped when the component that explains it is also selected ("Net Premiums Written −2.0%" beside "Segment A −2.5%" is one finding stated twice — the component wins).

**A divergent metric is never a top upgrade or a top downgrade.** When a line is revised up for the quarter and down for the year, calling it either states half the fact. Every divergent line is excluded from the curated lists in `prepare_revisions.py` (FCF and OCF both go when both diverge) and surfaces as a divergence finding where it explains the revision thesis.

**Contradiction detection and ranking.** The most investment-relevant revision stories are rarely "everything went up". `intel.contradictions` tests segment mix, revenue vs margin, revenue vs EPS, revenue vs FCF, EBITDA vs FCF, near-term vs outer-year, same-metric cross-horizon divergence, estimates vs share price, and — the Variant's primary definition — the FINANCIAL REVISION against the OPERATING EVIDENCE (`finvsops`): the strongest contradicting row from `intel.evidence`, so the Variant is the strongest unresolved contradiction between what the estimates did and what the sub-industry's own demand indicators did, never simply the largest KPI revision. **The gate is investment relevance, not disagreement**: a contradiction mandates the Variant only when it creates a plausible ALTERNATIVE EARNINGS OUTCOME — a leading-indicator family (fwd-demand, volume-pricing, retention, credit, underwriting) at material weight. Two datasets pointing different ways in a non-leading family is supporting evidence, not a debate. Every test reports a severity on one common scale — **the share of the headline revision the contradiction calls into question** — so tests measured in bps, dollars and relative price can be ranked against each other. A contradiction must then clear a SECOND gate before it can mandate anything: **thesis relevance.** It has to live inside the estimate picture and bear on the central revision thesis. The price/revision gap is the clean failure case — it can be large (e.g. 22pp behind the index) and still not be a contradiction in the estimates, because it is the market's reaction to them. It corroborates an argument; it never sets one. The top-ranked RELEVANT contradiction becomes the **mandated subject of the Variant View** when it scores ≥ 0.45 (`intel.boundContradiction`); the audit warns if the written variant argues something softer. Below that threshold no contradiction binds and the Variant falls back to the coverage/confidence gap — which is the honest variant for a name whose numbers all point the same way. This is what makes two companies produce genuinely different reads from one framework: one company binds on segment mix, another on revenue↑/FCF↓, a third on nothing and argues next-platform coverage instead.

**The spine is family-resolved, never fixed (learned cold on a bank and an auto insurer).** Every PRIMARY standardized income-statement code (`IS_P_*`) is a statement row for whichever sub-industry carries it: a bank's P&L lives in `IS_P_2xx` (NII, non-interest income, provisions, PPNR) and an insurer's in `IS_P_4xx` (premiums written/earned, underwriting income, investment income); a fixed product-company list silently gutted both. The FTE chain (`IS_P_200/202/210/212`) is a registered flow, exactly like Ex-1x. CORE anchors resolve down ladders (revenue: GAAP → FTE → premiums earned → written; operating: EBITDA → PPNR → underwriting income). Financial-sector BS rows (loans, deposits, BVPS, CET1, %NCO, equity) enter only when the sheet resolves NO cash line and NO debt basis — a structural gate, not a sector list. Underwriting and credit ratios published as SD codes (Combined/Loss/Expense/Cat) are KPIs, never revenue segments, and only OPERATING ratios may enter the curated lists (≥25bp); a tax-rate wobble may not.

**Direction is never guessed (the worst class of silent error).** A standard statement code (main P&L, bank and insurer lines, OCF/capex/FCF, cash, assets, liabilities, debt) takes its direction from the prepare script's code table (`CODE_DIR`), whatever its label says; `references/sanity_check.py` holds its own separate list and fails a row that disagrees. Every other row (KPIs, unlisted codes) resolves by label: DOWN phrases are tested first on the label with parenthetical qualifiers stripped; a label matching neither list is UNKNOWN — excluded from breadth, barred from the curated lists, and given no green/red colouring on the sheet. Before this rule a rising Provision for Credit Losses or Combined Ratio rendered green. Segment rows are up-is-good BY CONSTRUCTION (they reconciled to the top line), whatever their cleaned label says. The resolved polarity is written once per row (`it.fav`) and is the only source the builder colours from; flow lines stored as negative outflows are not inverted twice, balance-sheet levels keep their label polarity, and the non-operating line follows the statement identity (see the colour rule in the workbook section).

**The revenue roll-up is basis-homogeneous.** Families form on measurement prefixes (premiums, revenue, income, fees); a subset mixing bases (NPW beside NPE) is refused even when it reconciles — a policy COUNT can reconcile to Total Revenue by arithmetic accident and would otherwise print as segment dollars. When no family reconciles, the deepest family is kept unfiltered: honest and homogeneous beats reconciled and wrong. When no families exist and no business subset reconciles, the coverage-without-overshoot fallback in the segment hard rule applies before geography. The reconciliation target is itself a ladder (Total Revenue → NPE → NPW → FTE revenue).

**Cross-industry rules from the six-ticker validation (a data-software name, a security-software name, a warehouse retailer, a memory maker, an athletic-apparel name, an EV maker).** Three general rules, no ticker exceptions: (1) **Retail comp-sales PERCENTAGE rows** ("% SSS (Ex-Gas)", "Comparable Same Store (%)", "% SSS - Total Revenue (Ex-FX)") are the sub-industry's defining demand KPI — they route to the KPI section like underwriting ratios and feed `intel.evidence` under volume-pricing; the money row ("SSS - Total Revenue") still enters the revenue roll-up. (2) **Non-USD reporters parse natively**: any currency marker ("$", "€/£/¥", or an ISO code prefix — "CNY31.2B", "HK$44") flags a monetary value; all money renders in millions of the REPORTING currency, coherent within one workbook, and carries that currency on the sheet and the panel (`Line Item (CNY M unless stated)`, `Δ CNY since print`, `CNY1.41bn`; `$` only for US dollars). The currency is read from the company's own estimate and actual values and written to `contract.meta.currency`; the price feed's `CURRENCY` is the currency the share TRADES in (USD for an ADR of a CNY reporter) and never sets it (a difference is noted in the build log). Write the narrative's amounts with the same prefix. (3) **Segment rows order primary-series before secondary-series** (`SD_P_*` then `SD_S_*`, numeric within a series) — the vendor numbers primary codes in the company's reported order, but comparing numbers ACROSS series can put an "Other" row above the main segment.

**The path sentence follows the classification.** A Spike & Fade path must never print the front-load hold sentence; the classifier's own note is the conclusion, and the agreement count only chooses the wording (broad vs headline-only).

**The cash tests read both horizons.** A contradiction can live in the annual and not the quarter: a post-print reset can cut FY FCF 10% against revenue up 5% while the quarter's FCF moves only −1% and sits inside the threshold. The rev/FCF and EBITDA/FCF tests take the WORSE of the two legs and name the horizon, so the claim stays checkable. Severity has two factors and needs both: the RATIO against revenue (is the cash move disproportionate?) and the absolute SIZE (a cash move reaches full weight at 10%). Ratio alone rewards a small cut against a small revenue move — FY FCF −2.0% against revenue +1.5% scores 1.33 on ratio and would wrongly outrank a $600m segment cut. When FCF swings negative the %-move is suppressed by design, so severity is computed in dollars instead.

**Cross-horizon divergence.** It renders under What Consensus Embeds as `<Metric> Divergence:` (`FCF Divergence: +2.0% for 3Q26 against −2.0% for FY2026. …`), beside the horizon ladder it qualifies, unless it is itself the bound contradiction — in which case the Variant carries it. The same metric revised up for the quarter and down for the year is ONE finding, not two — stated as what the data shows, never as the mechanism behind it, and worded by the row's polarity: a revenue-like line revised up for the quarter reads `The improvement does not carry through the full year`, a cost line revised up reads `The deterioration does not carry through` (the prepare script writes `fav` and `tail` on every divergence row; the builder only reads them). Only sign flips with both legs ≥1% qualify; balance-sheet rows are excluded (a stock measured at two dates diverging is arithmetic, not a contradiction) as are capital-return lines.

**Metric polarity, display side.** Polarity already drives the ▲/▼ arrows; the choice of *which metric to show* is separate. When a curated line is a cost line and the margin it governs moved ≥25bp, state the margin — the economic consequence — and carry the components as evidence: `Gross margin −108bp on COGS +6.6% vs revenue +2.1%`. Derived margins are computed on the statement's LEAD flavour (the row that is not a muted twin, whichever flow won), never on the GAAP twin (an `EBIT margin fell 180bp` read from the GAAP twin while the headline basis fell 90bp is wrong), and every margin the narrative quotes must be the one in `intel.derived`. The same lead-flavour rule governs every lookup of a dual-flavour line — the core probes, the EPS bridge and the revenue / EPS levels What Consensus Embeds prints (a GAAP-flow sheet quotes GAAP EPS there, never the adjusted twin). Derived margins are **not consensus line items**, so they are barred from the evidence table (every row there carries its own broker count and range) and appear only in the curated lists and narrative text, always quoted with their components.

## The workbook (LOCKED format — do not restyle)

House look, shared with the other InSync skills: pure-white background, light hairlines only where data sits, black header bars, orange InSync accents, frozen first column + header rows, fit-to-width printing.

**Column widths (sheet 1):** column A is sized to the longest row label on the sheet — bold 10pt Calibri runs ≈0.87 width units per character, a GAAP twin adds its indent — clamped to [25, 40] as Excel DISPLAYS it (the xml width carries Excel's +0.71 padding), so a typical sheet stays at 25 and a software name widens to 38 for `Software License Renewals & Product Support Services`. Labels are NEVER shrunk to fit and never truncated inside the cap; the prepare script applies controlled abbreviations to known long standardized labels once (`Remaining Performance Obligations (RPO)` → `RPO`, `(Ex-Operating Lease)` → `(Ex-Op Lease)`, ` and ` → ` & `, spacing variants of the adjusted qualifier (`(Ex - 1x Item)`, `(Ex- 1x Items)`) → `(Ex-1x)`, the vendor's long form of the registered GAAP net-income code `Net Income (Loss) from Continuing Operations` → `Net Income`, so its twin renders `Net Income (GAAP)` on every ticker; segment metric suffixes dropped and a qualified metric tail folded into a parenthetical, `Wholesale - Core Brand Revenue` → `Wholesale (Core Brand)`) so the same label serves the table, the contract and the panel. Only a label that still exceeds the 40 cap is shortened with an ellipsis, and none of the standardized vocabulary does. The numeric columns are sized to their content: anchors/Current at least 10 (wide enough for the `Same as Current` marker) and Low/High at least 9, both widened to the longest formatted value on the sheet up to 15, so a bank balance sheet in $M (`4,800,000.0`) or a unit count (`55,400,000.0`) never renders as `###`; Δ$ and %Δ 12; YoY/Seq 7; Broker cnt 8 so the narrative panel gets the freed screen space. The `colW()` table in the renderer's masthead block MUST mirror the declared widths. The YoY/Seq number format is value-adaptive — `0.0%` below 100% in magnitude, `0%` at or above it (`(122%)`, `352%`) — so a large growth figure never renders as `###`.

**Panel prose wrapping:** the line budget is 136 characters (measured against the merged panel width at the PDF metric; a tighter budget orphans single words onto their own row). When a bullet DOES wrap, every continuation row is rendered as a rich-text run with the SAME face as the first line's body text (plain weight, the section's color) — never with the cell style's font, which for labelled bullets is bold and would change the face mid-sentence.

**ESTIMATE REVISIONS block:** the band title is the bare section name; the forecast period is carried by the sub-labels (`Upgrades (2Q27)` / `Downgrades (2Q27)`), never by a date parenthetical in the band. Upgrades and Downgrades render SIDE BY SIDE, row-aligned, because the contrast is the point of the block and both lists are short by construction (max 3 / max 2, never padded). The Downgrades column starts at the first panel-column boundary that clears the longest upgrade line plus a small gap — close enough to read as one block, adaptive to line lengths, never overlapping. The empty states (`No material upgrades identified (2Q27).` / `No material downgrades identified (2Q27).`) render in their header positions, and the column split accounts for the empty-state text.

**Sheet tab name:** the ONE sheet is `Revision Summary` — no ticker prefix; the masthead already names the company.

**Verdict-line lint exemption:** the "every movement claim carries a number" audit skips lines opening `Variant Assessment.` — that line's job is the fixed verdict plus one judgment sentence, and its figures live in the Potential Variant line directly above by design.

**Masthead (sheet 1 only, ONE row):** the InSync logo image sits at the left of column A, sized to the single 26pt row. The identity sits inline in cell A1 as one rich-text string — a leading 10pt space run that clears the logo (space width is a font metric, so the clearance is identical in Excel and the PDF renderer, unlike alignment indent units, which the two map differently), then the company name + ticker (bold 14), then "Revision Analysis" in muted 12pt. The same row carries both dates inline in tearsheet style (orange bold label + black value): "Prepared: {date}  ·  Expected Earnings Date: {date}". The dates sit UNMERGED in the FIRST PANEL COLUMN (P0), directly above the panel's status band, left-aligned and spilling right — on screen beside the table without scrolling, and the identity has the whole table width to itself, so the product name is always shown. The sheet prints fit-to-width, so the row is never split across pages. A width guard still measures the identity against the table width and drops the product name only if the two texts could ever meet, which no standard geometry produces. A hairline orange rule (bottom border) closes row 1 across the full width including the narrative panel; the period band starts at row 2, so the panel's phase band aligns with it. Sheet 1 freezes at B5 (masthead + band + header + date rows).

- **Δ columns are live Excel formulas** (recalculated on open, with cached values embedded) — `Δ$ = Current − Pre-Print`, `%Δ = (Current − Pre-Print)/|Pre-Print|`; % rows (margins, ETR) move in **bps** instead. YoY/Seq growth prints only when the base is positive AND the current value is not negative: a series that flips sign (working capital swinging from an inflow to an outflow) has no meaningful growth rate and the cell stays empty, the Δ$ column carrying the move; a negative-stored flow (capex) never shows growth.
- **Colour = favourable vs unfavourable revision, not direction.** Upward revisions green for revenue/profit/FCF-type lines; expense, tax, TAC, capex, share-count and debt lines are inverted automatically (downward = green). ⛔ **The polarity has ONE source: the prepare script writes `it.fav` (`up` / `down` / `null`) for every row and the builder only reads it.** Re-deriving direction from the label without a storage-sign check would colour a cut in spending ("Less: Capex", stored negative) red while the panel listed it as an upgrade. Rules inside `fav`: segments are up-by-construction; a FLOW line stored as a negative outflow is not inverted a second time; a STOCK line (balance sheet) keeps its label polarity even when negative (Net Debt of −$200m is net cash, and a rise toward zero is still unfavourable); the non-operating line (`IS_P_115/116`, `1003/1004`) takes its polarity from the STATEMENT IDENTITY, not the label — the script tests whether `EBIT − line` or `EBIT + line` reproduces PBT on current values (some feeds store it as a positive expense, others as income) and the same resolution drives the engine's contribution sign and the EPS bridge, disclosed in `flowNotes`; forward-demand KPIs (billings, bookings, book-to-bill, deferred revenue, RPO), PBT and cash levels are up-is-good; a label matching nothing stays uncoloured. A `Current X` / `Non-Current X` KPI whose consensus exceeds its parent `X` fails the family identity and cannot be reconciled: it is removed from the visible table and kept with its values in `contract.excluded` (see the visible-is-not-revisable rule).
- **Dispersion** = Low / High / broker Count from the latest snapshot OF THAT BLOCK'S PERIOD — the quarter block from the `q` history, the annual block from the `fy1` history — so no dispersion figure ever mixes periods; the period is named in each block's band (`NEXT QUARTER - 2Q27`, `FY2027`). Median/Std-Dev are not exposed by the MCP. The revision-momentum machinery (`intel.metrics`: velocity, persistence, convergence) reads only the quarter's post-print snapshots and is never displayed.
- **History matrix** = one column per update date since the print, forward-filled — computed into `contract.history` for the intelligence layer and audit only; it is never rendered as a sheet.

## Intelligence-layer guardrails (encoded in the prepare script — do not override)

- **Negative/sign-flipping bases**: %Δ is suppressed (null) whenever the base or current value is ≤ 0 (FCF swinging negative, net-debt lines) — the $Δ carries the signal in tables and template sentences instead. Velocity thirds are % only on all-positive series; the regime classification runs on $-moves so it always exists.
- **Storage-sign awareness**: expense lines stored as negative values (e.g. "Less: Capex" = −52,000) are NOT direction-inverted a second time — their sign already encodes economics. This applies to FLOW lines only; a negative balance-sheet level keeps its label polarity (see the colour rule above).
- **The `Cash flow.` driver line states both legs with their true signs** — `OCF −$2.0bn, capex spend −$1.5bn, FCF −$500m. The cut sits in operating cash flow, not capital spending.` — and names the leg that carried the FCF change. Capex is expressed as SPEND whatever the storage sign; the line never assumes an FCF cut came from higher capex.
- **The Variant owns its subject**: a contradicting operating indicator that clears the Variant gate (leading family, material weight) is removed from the curated Upgrades/Downgrades lists — its homes are the `Forward evidence:` line and the Variant, and a third appearance is the repetition the audit flags.
- **Takeaways** rank by weight × |move|, exclude the Balance Sheet section, and fall back to $Δ text when %Δ is suppressed.
- **The EPS bridge always shows a "consensus mix residual"** — broker models don't tie, and pretending they do would be dishonest. Revision quality (High/Medium/Low) is classified from the operating share of the explained move.
- **Watchlist reasons are prioritised for diversity** (FCF cut → FY2 non-confirmation → reversing regime → momentum-without-convergence → high persistence → max 2 reversal-risk entries).
- **Read-through sentences are fixed templates** filled only with computed values — never free-written.
- If a data pull for an intelligence block returns nothing (no call dates, no prices, no prior-cycle history), that block is silently omitted — the workbook still builds.

## Data quirks the scripts handle

- **BROKERCOUNT resets after a print** (drops to a handful, rebuilds over ~2 weeks as brokers refresh). That is why the T+10 anchor exists — comparing Current to the thin day-after consensus overstates moves. Mention thin counts in the run summary in chat (never on the panel) when the latest `Broker cnt` is below 5; rows under 3 brokers stay visible but never feed a revision conclusion (the visible-is-not-revisable rule).
- **YoY/Seq growth** is computed by the prepare script from reported actuals (Current consensus vs the just-reported and year-ago quarters) so it ties exactly to the level columns on the same row. The MCP also publishes dedicated growth codes (`IS_P_101-Y`, `IS_P_101-Q`, `KM_P_1008-Y`, …) which carry their own estimates, dispersion and revision history; those are **broker-averaged growth rates** and therefore differ slightly from growth computed off consensus levels (typically within about 0.1pp). Both are legitimate — the level-consistent version is used here so no two cells in a row can contradict each other.
- **Different codes update on different days.** A batch pulled "as of today" can mix an 08-10 vintage for levels with an 08-19 vintage for growth codes. The `Current` column always carries its own `UPDATEDATE`-derived date in the header, so never assume one as-of date for the whole sheet.
- **Key-Metric units are learned, never assumed.** Each `KM_*` code's scale and monetary/count class come from its actuals rendering (see the KM hard rule in SKILL.md). If an estimate for a KM code still sits ≥100× away from its reported actual, the script does NOT silently rescale it — it records a caution in `contract.scaleNotes` and the build log (nothing prints on the sheet; relay it in the run summary), because inventing a unit is worse than flagging one. Cross-check available: computed headcount YoY matches the MCP's own `KM_P_1008-Y` growth code.
- **Adjusted twins are sparse and inconsistent in depth.** `IS_P_128` (EPS Ex-1x & SBC) can carry 9 brokers while the secondary `IS_S_657` (EPS Ex-SBC) carries 40 — the script prefers the deeper series for revision work, since a 9-broker line produces far noisier revisions. Both appear on the sheet when both return.
- **Fresh prints** (< 10 days ago): T+10 is not yet eligible, so the sheet shows Pre-Print | Current; when no broker has refreshed yet the band states it and every Δ prints `–` (see the data-state rule). Say so in the summary.
- **Anchor columns are elapsed-time-gated for eligibility and information-gated for visibility.** Never render a T+10 or T+40 column for a window that has not happened yet, and never render one whose every row equals its neighbour; the prepare script emits `anchors` (eligible) and `anchorView` (distinct per block), and the builder lays out the union — a run 12 days after a print with a still-moving consensus shows Pre-Print | T+10 | Current; a run on day 15 with no update since day 9 shows Pre-Print | Current.
- **The non-operating line's sign convention differs by name and by period.** a forecast feed can store `Net Interest & Other Income/Expense` as a positive expense while some of the actuals are stored as negative income; the polarity is resolved from the statement identity on consensus values (above), but a YoY/Seq growth computed against an actual stored with the opposite sign is meaningless (e.g. +410% on that row against an annual actual built from mixed-sign quarters). So the sheet shows NO YoY/Seq growth on the net interest lines (`IS_P_115/116/1003/1004`; the reason is kept in `contract.flowNotes`); the level and the Δ are right. On any other money row, growth above ±300% measured on a base under 1% of revenue is printed but warned in the build log and `contract.scaleNotes`: relay it in the run summary.
- **Annual-only lines** (some KPIs, guidance-style items) show in the FY blocks with a blank quarter block.

## Computed panel lines

- **What Consensus Embeds.** Key levers print only when the dominant lever is not the top line; cycle rank only when at least four prior cycles carry data on the like-for-like pre-print basis AND the current cycle is the extreme of the sample **by MAGNITUDE** (general rule: a −5% EPS cut against prior cuts of −15% to −40% is the SMALLEST revision of the sample; ranking by signed value called it "the largest EPS revision" and "an unusually strong repricing") — when revenue and EPS are both extremes the one further from its prior-cycle median carries the line, and a sign flip against every prior cycle is stated as such (`the only post-print cut to EPS in the last 5 cycles (prior-cycle median +5.0%)`); the renderer words it so the statistic SUPPORTS a conclusion about the current reset rather than standing alone as one; the `Read-through:` line prints only when the outermost period with data moves in the SAME direction as the near quarter, by more than 1.5× its magnitude AND at least 0.5pp more (`The revision strengthens further out.` for an upgrade, `The cut deepens further out.` for a downgrade); a cut that fades further out prints nothing. The horizon ladder reads ONE flavour — the statement's lead revenue / EPS code — so its first point is the headline revision; another code fills a period only when it is the same series (levels within 0.5%).
- **Operating evidence (`intel.evidence`).** Operating KPIs enter the drivers block only through the single `Forward evidence:` line, where `intel.evidence` classifies each material KPI move as CONFIRMING or CONTRADICTING the revision, tagged with its economic driver family resolved from the LABEL — fwd-demand (RPO/billings/bookings/backlog/book-to-bill), volume-pricing (ASP/units/bits sold/deliveries/traffic/comps-SSS/subscribers), retention (NRR/churn), credit (provisions/charge-offs), underwriting (loss/combined ratios), capacity (headcount/stores). Sector → sub-industry → driver family is resolved generically from labels, never from ticker templates: the same logic yields billings for software, deliveries/ASP for autos, ASP/bits sold for memory semis, loss ratios for insurers, credit costs for banks, comparable-sales for retail. A KPI whose polarity cannot be resolved, or whose move is immaterial, is NEUTRAL — excluded from the evidence read rather than forced onto a side; and evidence is RANKED (economic relevance to the debate × materiality × thesis sensitivity × coverage depth), never majority-voted: one highly relevant contradicting indicator outweighs several low-relevance confirming ones. (A bridge line such as "Non Current RPO" is conceptually wrong on any ticker; the engine excludes it structurally.)
